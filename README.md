# krine — 판단 일기

> 하루의 선택을 판단 구조로 남기고, AI의 반박에 재반박하며 검증하고, 조건이 바뀌면 다시 꺼내 재판단하는 판단 기록 서비스.

**🔗 데모: https://krine-minwu06255-5571s-projects.vercel.app** (모바일 뷰포트 권장)

---

## 서비스 소개

### 어떤 서비스인가요?

krine은 중요한 결정을 내리는 과정에서 자신의 판단 구조를 정리하고,
AI의 반박을 통해 스스로 검증할 수 있도록 돕는 판단 기록 서비스입니다.

사람은 매일 수많은 결정을 내리지만, 결정의 결과만 기억할 뿐
어떤 판단 기준과 근거를 사용했고, 어떤 대안을 검토했으며,
어떤 조건에서 그 판단을 내렸는지는 명확하게 남기지 않는 경우가 많습니다.

krine은 이러한 판단 과정을 기록하고 구조화하여,
사용자가 자신의 결정을 설명하고, 새로운 조건에 맞게 수정하며,
과거의 판단을 다시 활용할 수 있도록 돕습니다.

### 누구를 위한 서비스인가요?

업무와 일상에서 중요한 결정을 자주 내리고,
자신의 판단을 돌아보고 설명하거나 수정하고 싶은 사람을 대상으로 합니다.

예를 들어 다음과 같은 상황에서 사용할 수 있습니다.

- 프로젝트의 기술이나 방향을 결정해야 할 때
- 여러 대안 중 하나를 선택해야 할 때
- 이직, 학습, 구매 등 중요한 개인적 결정을 내릴 때
- 과거에 내린 결정을 다시 검토해야 할 때
- 다른 사람의 반박이나 질문에 자신의 판단을 설명해야 할 때

### 해결하려는 문제

krine은 판단 과정에서 발생하는 다음 세 가지 문제에 주목합니다.

1. **결론만 남는다** — 어떤 대안을 어떤 기준으로 비교했는지 남지 않습니다.
2. **검증 없이 넘어간다** — 자신의 판단에 반박을 제기하고 스스로 재검토하는 과정이 부족합니다.
3. **판단이 축적되지 않는다** — 과거에 어떤 기준과 조건으로 판단했는지 다시 꺼내 활용하기 어렵습니다.

## 실행 방법 (심사자 가이드)

### 데모로 체험하기 (권장)

**https://krine-minwu06255-5571s-projects.vercel.app** 을 모바일 뷰포트(개발자 도구 → 모바일 모드, 390px 권장)로 열어주세요. 시드 데이터가 들어 있어 바로 체험할 수 있습니다.

**추천 체험 순서 (약 5분):**

1. **재검토 루프** — 홈 상단 "재검토가 도착했어요" 카드 → [다시 보기] → 조건 확인 → [유지/수정/뒤집음] + 이유 → 카드 상세의 "판단의 변화" 타임라인에 새 버전이 쌓인 것 확인. "아직이에요"를 누르면 큐의 다음 항목으로 이어집니다.
2. **판단 기록 (핵심 플로우)** — 홈 [판단 기록하기] → 오늘 한 선택을 자유롭게 작성 → AI가 판단을 발견해 제안 → 적응형 질문에 하나씩 답변 → 비교표 확인·수정(셀 탭) → 반박 받기(선택) → 재반박 → 저장. *AI는 답을 쓰지 않고 질문만 합니다.*
3. **반박·재반박** — 아카이브 → 아무 판단 카드 → [반박 받기] → AI의 반박에 재반박 → [방어했다/판단을 수정한다/보류]. 보류하면 재검토 큐로 돌아옵니다.
4. **아카이브** — 하단 탭 → 제목·태그로 검색.

### 로컬 실행

요구 사항: Java 17+, Node.js 18+. 외부 의존 없음 (DB는 H2 file, **LLM 키가 없으면 내장 mock으로 전체 플로우 동작**).

```bash
# 1. 백엔드 (http://localhost:8080) — 첫 실행 시 시드 데이터 자동 삽입
cd backend && ./gradlew bootRun

# 2. 프론트엔드 (http://localhost:3000) — 새 터미널에서
cd frontend && npm install && npm run dev
```

실제 LLM 연결(선택): `backend/.env`에 `OPENAI_API_KEY=키` + `LLM_PROVIDER=openai` (또는 `GEMINI_API_KEY`). `LlmPort` 추상화로 provider는 설정만으로 교체됩니다.

## 어디까지 만들기로 했고, 무엇을 뺐는지

**범위 원칙**: 넓게 벌리는 대신, "기록 → 구조화 → 반박 검증 → 축적 → 재검토"라는 코어 루프 하나를 끝까지 완성했습니다. 공유를 뺀 자리는 **사용자 자신이 남긴 조건·약속이 재방문을 만드는 재검토 루프**가 리텐션을 담당합니다.

**만든 범위**: 일기에서 판단 발견 → AI의 후속 질문(한 번에 하나) → 판단 구조 정리(사용자가 직접 확인·수정) → AI의 반박에 재반박(원할 때만, 횟수 제한 없음) → 판단 카드로 저장(저장된 판단은 고쳐 쓰지 않음) → 아카이브에서 검색 → 때가 되면 다시 검토(조건 날짜가 됐을 때 · "발생했나요?" 확인 · 다시 보기로 한 날 · 답을 보류했던 반박) → 재검토 결과는 원본을 그대로 남긴 채 새 버전으로 쌓임.

**의도적으로 뺀 것:**

| 뺀 것 | 이유 |
|---|---|
| 공유·피드·투표 | 유저 수의 의존으로 인해서 제외 |
| AI 생성 주간 요약 | 운영을 성립시키는 기능이지만 시간 부족으로 인해서 기각 |
| 로그인 | 단일 사용자 데모 범위로 제외 |

## 구현한 것 vs 기획·설계로 대체한 것

### 구현 완료

- 기록 5-Step 플로우: 판단 발견 → 적응형 질문(한 번에 1개, 최대 4개) → 구조화 승인 → 반박·재반박 → Reflection
- 실제 LLM 연동: Gemini/OpenAI/Mock 전환(`LlmPort`), 톤 가드레일(답 대필·공감·진단·평가 금지), 429/503 자동 재시도(`Retry-After`), 호출별 토큰 로깅(`LLM_USAGE`)
- 판단 카드(저장 후에는 고칠 수 없음) + 재검토 때마다 원본 위에 새 버전이 쌓이는 타임라인, 아카이브 검색(제목·태그)
- 재검토 루프: 4가지 계기(조건 날짜 도래·발생 확인·다시 보기 약속·보류 반박)를 모아 보여주는 큐, 하나씩 이어보기, 당시 기록 함께 표시
- 시드 데이터(실행 즉시 재검토 큐 데모), 백엔드 테스트 12건, Railway/Vercel 배포

### 기획·설계로 대체

- **판단 패턴 리포트** — "자주 쓰는 기준" 등. 데이터 축적이 전제. AI 요약이 아니라 원시 데이터+차트 중심으로 설계
- **푸시·이메일 리마인더 / 계정·인증(현재 단일 사용자)**
- **지속 운영을 위한 관리·데이터 관점** — 아래에 기획으로 정리

### 운영·데이터 관점 (기획으로 대체)

운영자가 관리해야 하는 영역은 **사용자 / 판단 데이터 / AI·시스템** 세 축이며, 이 서비스는 특성상 **LLM 운영이 하나 더 추가**됩니다.

**① 운영 대시보드** — 서비스 현황(활성 사용자·판단 생성·반박 시작·완료), AI 지표(판단 추출 성공률·질문 생성 성공률·반박 완료율·LLM 평균 응답시간·오류율·일 비용), 재검토 지표(예정·완료·미완료). "기록은 많은데 반박에서 이탈한다" 같은 신호를 여기서 발견합니다.

**② LLM 운영 (가장 먼저 문제가 되는 지점)** — 판단 1건에 발견→질문×4→구조화→반박→되비추기까지 **약 8회 호출**이 발생하므로(현재도 호출별 `LLM_USAGE` 로그로 단계·토큰 관측) 사용자가 늘면 비용·latency가 첫 병목입니다. 단계별 호출량·모델별 latency·토큰·실패율·비용과 함께 **Prompt Version 관리**가 필수입니다: 프롬프트를 개선하면 과거 데이터와 결과가 달라지므로, 판단 데이터에 `model`, `promptVersion` 메타데이터를 남겨 "v2부터 구조화 정확도가 떨어졌다"를 추적 가능하게 설계합니다.

**③ 데이터 설계 원칙** — 핵심 엔티티는 User가 아니라 **Judgment(판단)**입니다. 그리고 **원본(Raw)과 구조화 데이터(Structured)를 분리**합니다: 사용자의 원문 일기 → LLM 추출 → **사용자 승인**을 거친 것만 최종 판단으로 저장 (**AI 추출값 ≠ 최종 판단**). 확정 후에는 원본을 덮어쓰지 않고 새 버전으로만 쌓아 사후 편향 없이 데이터 무결성을 지킵니다 — 이 원칙은 현재 구현(원문 일기 보존, 구조화 승인 단계, 불변 버전)에 이미 반영되어 있습니다.

**④ 개인정보·삭제** — 판단 일기는 매우 개인적인 데이터입니다. 운영 화면은 판단 ID·상태·생성일·LLM 처리 상태 등 **메타데이터 중심**으로 구성하고, 원문 열람은 제한적으로만 허용합니다. 계정 정지·데이터 삭제 요청 처리가 최소 운영 기능입니다.

**⑤ 서비스가 커지면 무엇이 먼저 문제가 되는가**

| 단계 | 먼저 터지는 문제 |
|---|---|
| 초기 | **LLM 품질** — 잘못된 구조 추출, 이상한 반박 → 사용자 이탈 |
| 사용자 증가 | **LLM 비용·latency** — 호출량 증가 |
| 데이터 증가 | **검색·집계** — 아카이브 조회, 기준별 통계 부담 |
| 더 큰 규모 | **AI 품질 관리** — 모델·프롬프트 변경 시 과거 데이터와의 일관성 |

## 기술 스택과 선택 이유

**Next.js와 Spring Boot를 선택한 이유는 단순합니다 — 제가 가장 익숙한 프레임워크이기 때문입니다.** 짧은 기한 안에서 스택 선택의 기준은 "무엇이 더 좋은가"가 아니라 "문제가 생겼을 때 내가 즉시 원인을 찾고 고칠 수 있는가"였습니다. 특히 AI 도구가 코드를 많이 생성하는 작업 방식에서는, 생성된 코드를 제가 읽고 검증하고 직접 수정할 수 있어야 개발 속도와 품질을 모두 통제할 수 있다고 판단했습니다.

| 레이어 | 선택 | 이유 |
|---|---|---|
| Backend | Spring Boot 3.5, Java 17, Gradle, Lombok, Spring Data JPA | 가장 익숙한 백엔드 스택 — AI가 생성한 코드의 JPA 함정(merge, lazy loading)을 직접 잡아낼 수 있었음. "판단 이력은 덮어쓰지 않고 쌓기만 한다"는 도메인 규칙을 엔티티 설계로 강제 |
| DB | H2 (file) | 외부 의존 없이 심사자 즉시 실행. 단일 사용자 데모에서는 재배포 시 시드 리셋이 오히려 데모 품질을 보장. 확장 시 Postgres 전환 지점 |
| Frontend | Next.js (App Router), TypeScript, Tailwind CSS, TanStack Query | 가장 익숙한 프론트 스택 — 컨벤션을 [`frontend/RULES.md`](frontend/RULES.md)로 먼저 정해두고 AI 생성 코드가 그 규칙 안에서 움직이게 통제 |
