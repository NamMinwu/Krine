# krine — 판단 일기

> 하루의 일상 속에서 **판단의 순간을 발견**하고, 그 판단을 **구조화·검증**해 **다시 꺼내 쓸 수 있게** 하는 판단 일기.

사람은 매일 결정을 내리지만 결론만 남습니다. 어떤 대안을 어떤 기준으로 비교했는지는 사라지고, 반대 관점에서 검증받지 못하고, 조건이 바뀌어도 과거의 판단을 다시 꺼내지 못합니다. krine은 이 세 가지 실패 지점을 하나의 루프로 해결합니다.

```
일상 회상 → 판단 발견 → 기록(적응형 질문) → 구조화(비교표, 사용자 승인)
→ 반박·재반박(Objection) → 판단 카드 확정(불변) → 아카이브
→ [조건 도래 / 사건 체크인 / 보류 반론] → 재검토 → 새 버전(유지·수정·뒤집음)
```

일기는 UX의 껍데기이고, 핵심 객체는 **Judgment(판단)**입니다. 판단은 Git 커밋처럼 **불변 버전**으로 쌓입니다 — 원본은 수정할 수 없고, 재검토할 때마다 새 버전이 추가됩니다(사후 확신 편향 방어).

**누구를 위한 것인가**: 업무·일상에서 중요한 결정을 자주 내리고, 자신의 판단을 설명하거나 새로운 조건에 맞게 수정하고 싶은 사람.

## 실행 방법

요구 사항: **Java 17+**, **Node.js 18+**. 외부 서비스 의존 없음 (DB는 H2 file, LLM은 키 없으면 내장 mock으로 동작).

```bash
# 1. 백엔드 (http://localhost:8080) — 첫 실행 시 시드 데이터 4건 자동 삽입
cd backend
./gradlew bootRun

# 2. 프론트엔드 (http://localhost:3000) — 새 터미널에서
cd frontend
npm install
npm run dev
```

브라우저에서 `http://localhost:3000` 접속 → 홈 상단에 **"재검토가 도착했어요"** 카드가 바로 보입니다(시드에 만료일이 지난 조건이 들어 있음). 모바일 뷰포트(375~430px) 기준으로 설계되어 있어 개발자 도구의 모바일 모드로 보면 가장 좋습니다.

### 실제 LLM 연결 (선택)

키가 없으면 자동으로 **mock LLM**이 사용되어 전체 플로우가 동작합니다. 실제 LLM을 쓰려면:

```bash
# backend/.env 파일 생성 (자동으로 로드됨)
GEMINI_API_KEY=your-key
```

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `GEMINI_API_KEY` | (없음) | 있으면 Gemini 사용 |
| `OPENAI_API_KEY` | (없음) | 있으면 GPT 사용 (Gemini 키가 없을 때) |
| `LLM_PROVIDER` | `auto` | `gemini` / `openai` / `mock` 강제 지정 가능 |
| `GEMINI_MODEL` | `gemini-3.6-flash` | |
| `OPENAI_MODEL` | `gpt-4o-mini` | |

LLM은 `LlmPort` 인터페이스 뒤에 있어 provider를 설정만으로 교체할 수 있습니다.

> Gemini 무료 티어는 **모델당 하루 20회** 제한이 있습니다. 429(쿼터 초과)가 나면 `.env`에 `GEMINI_MODEL=gemini-2.5-flash`처럼 다른 모델을 지정하면 됩니다(쿼터는 모델별로 분리). 일시적 503은 클라이언트가 1회 자동 재시도합니다.

### 테스트

```bash
cd backend && ./gradlew test   # 도메인·API·LLM 플로우 테스트 12건
```

## 핵심 사용 흐름 (5-Step)

| Step | 화면 | 무엇을 하나 |
|---|---|---|
| 1 | 일기 | 하루를 자유롭게 쓰면 LLM이 그 안의 **판단 후보를 발견**해 제안 ("A vs B 판단으로 기록해볼 수 있어요") |
| 2 | 적응형 질문 | 빠진 조각(대안·기준·포기한 것·변경 조건)만 골라 **한 번에 하나씩**, 최대 4개. 선택지 버튼 + 직접 입력 |
| 3 | 구조화 | LLM이 "제가 이해한 판단이 맞나요?" 톤으로 **비교표** 제시. 모든 셀 수정 가능. 변경 조건은 **시점형(📅)/사건형(👀)** 자동 분류, 시점형이 없으면 30일 뒤 재검토 제안 |
| 4 | 반박 (Objection) | **버튼을 눌러야 시작**(옵트인). LLM이 반론을 하나씩 제시하면 내가 답하고, **방어 / 수정 / 보류** 중 하나로 종결. 보류는 재검토 큐로 |
| 5 | Reflection | "처음 표현 vs 지금 결론"을 나란히 보고 저장 → 판단 카드 확정(잠금) + v1 생성 |

이후 **재검토 루프**: 시점형 조건이 만료되거나, 사건형 조건 체크인, 보류한 반론이 홈 상단 큐로 돌아옵니다 → 유지/수정/뒤집음으로 재판단 → 새 버전이 타임라인에 쌓입니다.

## 왜 이렇게 만들었나 (핵심 설계 결정)

- **리텐션을 공유가 아니라 재검토 루프로**: 피드·투표식 리텐션은 유저 수에 의존합니다(콜드 스타트). 대신 사용자가 기록할 때 남긴 "판단을 바꿀 조건"이 미래의 자신을 다시 부르게 했습니다. 콘텐츠(판단 카드)가 쌓일수록 재방문 이유도 쌓이는 구조입니다.
- **원본 불변 + append-only 버전**: 결정 저널 방법론의 핵심은 "기억은 결과를 알면 재작성된다"는 사후 확신 편향 방어입니다. 확정된 판단은 수정 API가 409로 거부하며, 재검토는 새 버전만 추가합니다.
- **LLM은 답을 쓰지 않는다**: 시스템 프롬프트에 가드레일 명문화 — 공감 금지, 진단 금지, 평가·점수화 금지. 허용되는 것은 분석 질문과 되비추기뿐. 구조화 결과도 사용자가 승인·수정해야 저장됩니다.
- **재검토 큐는 파생 뷰**: 별도 큐 테이블 없이 조건 상태 + 보류 반론에서 조회 시점에 계산 — 상태 중복과 동기화 버그를 원천 차단.

### 의도적으로 뺀 것들

| 뺀 것 | 이유 |
|---|---|
| 공유·피드·투표 | 유저 수에 의존하는 외재적 리텐션. 내 데이터가 나를 부르는 내재적 루프로 대체 |
| 스트릭·연속 기록 배지 | 레퍼런스 리서치 결과 신규 사용자 이탈을 막지 못하고, 깊이 중심 제품에 피상적 참여만 유인 |
| AI 멘토 페르소나 | 판단을 외부 권위에 미루게 함 — "자기 기준 강화"라는 핵심 가치와 정반대 |
| AI 생성 주간 요약 | 기록의 소유권이 AI로 넘어감 ("AI가 그렇다니까") |
| 판단 점수화 | "당신의 판단은 72점"이 아니라 "당신의 판단을 이렇게 이해했습니다" |

## 구현 범위

### 구현한 것

- 기록 5-Step 플로우 전체 (판단 발견 → 적응형 질문 → 구조화 승인 → 반박 → Reflection)
- 실제 LLM 연동 (Gemini 기본 / OpenAI 교체 / mock 폴백) + 톤 가드레일
- 판단 카드·아카이브 (주제 태그·상태 필터, 버전 타임라인)
- 재검토 루프 (시점형 자동 도래·사건형 체크인·보류 반론 → 유지/수정/뒤집음 → 새 버전)
- 작성 중 이탈 대응 "이어서 하기" (대화 서버 저장 + flowStep 재개)
- 시드 데이터 4건 (실행 즉시 재검토 큐가 보이도록 만료 조건 포함)
- 백엔드 테스트 12건 (도메인 상태 전이·큐 계산·API·LLM 플로우)

### 기획·설계로 대체한 것 (구현 안 함)

- **판단 패턴 리포트** — "자주 쓰는 기준", "자주 흔들리는 전제" 등. 데이터 축적이 전제라 MVP에서 제외. AI 요약이 아니라 원시 데이터+차트 중심으로 설계 예정
- **판단 트리 캔버스 시각화** — 현재는 비교표가 담당. Heptabase식 노드 뷰는 로드맵 (LLM이 배치, 사용자는 내용만 수정)
- **사건형 조건 정기 체크인 스케줄링 / 만료 조건 날짜 재설정** — 현재 만료 조건은 처리 전까지 큐에 남음
- **푸시·이메일 리마인더** — 모바일 웹 제약으로 "앱을 열면 홈 상단에 도착해 있다" 방식 채택. 확장 시 PWA 푸시
- **계정·인증** — MVP는 단일 사용자
- **관리자 화면** — 운영 지표(LLM 호출 실패율, 판단 생성 수, 재검토 전환율)는 설계 문서에 정의

기획·설계 문서: [`docs/superpowers/specs/`](docs/superpowers/specs/) (문제 정의·UX·데이터 모델), 구현 계획: [`docs/superpowers/plans/`](docs/superpowers/plans/)

## 기술 스택과 선택 이유

| 레이어 | 선택 | 이유 |
|---|---|---|
| Backend | Spring Boot 3.5, Java 17, Gradle, Lombok, Spring Data JPA | 가장 빠르게 움직일 수 있는 스택. append-only 버전 모델을 엔티티 설계(`@Setter` 제거)로 강제 |
| DB | H2 (file mode) | 외부 의존 없이 심사자가 즉시 실행, 재시작해도 데이터 유지 |
| Frontend | Next.js (App Router), TypeScript, Tailwind CSS, TanStack Query | 모바일 웹 단일 컬럼. 아키텍처 규칙은 [`frontend/RULES.md`](frontend/RULES.md) |
| LLM | `LlmPort` 추상화 — Gemini / OpenAI / Mock | provider 교체 가능 구조를 인터페이스로 증명. 키 없이도 데모 성립 |

## 데이터 모델

```
Decision (판단) — status: DRAFT → ACTIVE (단방향, confirm 시 잠금)
├─ DecisionOption[]   선택지 (얻는 것 / 포기하는 것)
├─ DecisionVersion[]  판단 버전 — append-only, @Setter 없음 ★
├─ Condition[]        변경 조건 — DATE(자동 도래) | EVENT(체크인)
├─ Objection[]        반론 — 방어/수정/보류, 보류는 재검토 큐로
└─ FlowMessage[]      기록 대화 로그 — "이어서 하기"의 근거
```

재검토 큐 = `Condition(DATE, 만료, PENDING)` + `Condition(EVENT, PENDING)` + `Objection(DEFERRED)`의 파생 뷰.

## AI 도구 활용

이 프로젝트는 Claude Code로 기획부터 구현까지 진행했습니다.

- **기획**: 문제 정의 → 솔루션 요구사항 → 레퍼런스 리서치(Mindsera, Rosebud, Stoic, Decision Journal, Day One을 병렬 리서치 에이전트로 조사) → UX 설계 → 설계 문서. 리서치에서 "재검토가 선택사항인 앱은 실패한다", "원본 불변이 사후 편향 방어의 핵심" 같은 설계 결정의 근거를 얻음
- **구현**: 태스크 단위 TDD (테스트 먼저 → 실패 확인 → 구현 → 통과 → 커밋). 프롬프트 4종(발견자/질문자/구조화/반박자)의 가드레일 설계
- **잘 안 된 것**: ① Spring Initializr가 Boot 4.1을 내려줘 계획(3.x)과 충돌 — 3.5로 수동 고정 ② JPA merge가 반환한 복사본과 로컬 참조가 달라 자식 엔티티 id가 null로 남는 버그 — flush 방식으로 수정 ③ open-in-view=false에서 lazy 컬렉션을 dto가 그대로 들고 나가 직렬화 시점에 터짐 — 트랜잭션 내 매핑 + 방어적 복사로 수정. 세 건 모두 AI가 낸 코드의 첫 실행에서 테스트로 잡음
