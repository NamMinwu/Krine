# krine — 판단 일기 서비스 기획·설계 문서

작성일: 2026-08-20 (v2 — 구현 과정의 결정 변경을 반영한 as-built 문서)
v1 → v2에서 뒤집힌 결정들은 §13 "설계 결정의 변화"에 이유와 함께 기록했다.

---

## 1. 한 줄 정의

> 하루의 일상 속에서 판단의 순간을 발견하고, 그 판단을 구조화·반박으로 검증해 다시 꺼내 쓸 수 있게 하는 **판단 일기**.

- 핵심 객체는 **Judgment(판단)**. 일기는 UX의 껍데기 — 진입은 일기처럼, 결과물은 판단 구조로.
- 판단은 한 번 쓰고 끝나는 글이 아니라 **버전을 가진 살아있는 기록** (v1 확정 → 반박 → 재검토 → v2 수정 → v3 뒤집음).

## 2. 문제 정의

사람은 매일 결정을 내리지만, 그 결정을 만든 판단의 구조(판단 기준·대안·근거·조건)를 자신의 언어로 정리하고 검증할 기회가 부족하다. 그래서 자신의 판단을 설명하거나, 새로운 조건에 맞게 수정하고 재사용하기 어렵다.

**실패 지점 3개**

1. **결론만 남는다** — 어떤 대안을 어떤 기준으로 비교했는지 남지 않는다.
2. **검증 없이 넘어간다** — 반박받고 스스로 재반박해보는 과정이 없다. 확신할수록 위험하다.
3. **판단이 축적되지 않는다** — 과거의 판단 기준과 조건을 다시 꺼낼 수 없다.

**타깃**: 업무·일상에서 중요한 결정을 자주 내리고, 자신의 판단을 돌아보고 설명·수정하고 싶은 사람.

## 3. 솔루션 요구사항 (공유 기능 제외)

| # | 요구사항 | 해결하는 실패 지점 | 구현 |
|---|---|---|---|
| R1 | 판단의 순간을 떠올리게 한다 — 회상 칩 + 판단 발견 + 적응형 질문 | 1 | 기록 5-Step |
| R2 | 결론이 아니라 판단 구조를 남긴다 — 비교표로 확인·수정 | 1 | 구조화 + 승인 |
| R3 | 사용자가 직접 반박·재반박한다 — LLM은 답을 대신 쓰지 않는다 | 2 | 반박 루프 (무제한) |
| R4 | 과거 판단을 검색하고, 조건이 바뀌면 수정할 수 있다 | 3 | 아카이브 검색 + 재검토 루프 |

공유(피드·투표·UGC)는 제외. 공유의 리텐션은 유저 수에 의존하는 외재적 루프이므로, **사용자 자신이 남긴 조건·약속이 재방문을 만드는 내재적 루프(재검토)**를 리텐션의 축으로 삼는다.

## 4. Core Loop

```
일상 회상 → 판단 발견 → 기록(적응형 질문, 한 번에 하나)
→ 구조화(비교표, 사용자 승인) → 반박·재반박(옵트인, 무제한)
→ 판단 카드 확정(불변) → 아카이브
→ [조건 도래·체크인·확인 약속·보류 반박] → 재검토(하나씩, 이어서)
→ 재판단(유지·수정·뒤집음 = 새 버전) → 아카이브
```

### 재검토 큐에 올라오는 4가지

| 종류 | 정의 | 트리거 |
|---|---|---|
| DUE_DATE | 시점형 조건 도래 | `Condition(DATE)`의 날짜가 지남 (자동) |
| EVENT_CHECKIN | 사건형 조건 체크인 | `Condition(EVENT)` 미확인 동안 "발생했나요?" |
| CHECK_IN | 확인 약속 도래 | `Decision.checkInDate` — 재검토하면 소진 |
| DEFERRED_OBJECTION | 보류한 반박 | 반박에서 "보류"로 종결한 것 |

큐는 별도 테이블이 아니라 위 데이터에서 조회 시점에 계산되는 **파생 뷰**다.
큐 처리 UX는 "한 번에 하나씩, 이어서" — 항목을 처리(또는 "아직이에요")하면 다음 항목으로 이동, 비면 홈으로.

### 개념 구분 원칙 (반복 적용된 설계 원칙: 다른 축을 한 위계에 섞지 않는다)

- **판단 기준** = 가치의 저울 (무엇을 중요하게 봤나 — 증명 불가, 변할 수만 있음)
- **변경 조건** = 반증 시나리오 (무엇이 일어나면 판단을 바꾸나 — 사건의 세계)
- **확인 약속(checkInDate)** = 달력의 세계 (언제 확인하러 올지 — 조건이 아님)
- **verdict(유지/수정/뒤집음)** = 과거의 이력 / **검토 대기** = 현재의 주의 — 서로 다른 축

### 불변 원본 원칙 (사후 확신 편향 방어)

확정된 판단 카드는 수정 불가(API가 409로 거부). 재검토는 원본을 편집하지 않고 **새 버전**(verdict + 이유)만 추가한다. Git 커밋 모델.

## 6. UX (모바일 웹, 세로 단일 컬럼)

### 네비게이션

- 하단 탭 2개: **홈 / 아카이브**. 몰입형 플로우(기록·재검토·반박)에서는 탭 숨김.
- 기록은 풀스크린 스텝 플로우(1/5 진행 표시), 채팅 말풍선 UI 금지 — 문서형 "질문 + 입력" 화면.

### 홈 — 하루를 돌아보는 ritual (정보 최소화)

```
[krine 워드마크 — 딥 플럼 히어로 패널]
좋은 저녁이에요. / 오늘 어떤 선택을 했나요? (세리프)
🔔 재검토가 도착했어요 (n) — 첫 항목 미리보기 + [다시 보기]   ← 있을 때만
[회상 칩 4개] [판단 기록하기]
내 판단 n개 모아보기 →
```

- 재검토 카드가 리텐션의 축이므로 최상단. 카드에는 **사용자가 남긴 조건 원문**을 되비춘다("판단을 저장할 때 이렇게 적어두셨어요").
- 최근 판단 리스트·이어서 하기 카드는 제거(아카이브와 중복, 정보 과밀).

### 기록 5-Step

1. **일기** — 자유 서술. 회상 칩으로 빈 화면 부담 제거.
2. **판단 발견 → 적응형 질문** — LLM이 판단 후보(A vs B)를 제안, 수락하면 빠진 조각(대안·기준·포기한 것·조건)만 **한 번에 하나씩** 질문(최대 4개). 선택지 버튼 + 직접 입력. *선택지 규칙: 탭하면 그 질문의 답으로 그대로 저장되는 문장만. A vs B 재나열 금지.*
3. **구조화** — "제가 이해한 판단이 맞나요?" 톤. 비교표(얻는 것/포기하는 것, 선택지 N개 — 2개 미만 금지, 3개 이상 가로 스와이프), 기준 칩, 조건(시점형/사건형 뱃지), 태그. **모든 요소 탭 편집 + 선택지 추가·이름 편집.** 시점형 조건이 없으면 별도 카드 "다시 볼 시점"에서 확인 약속(+30일)을 제안 — 사용자가 확정.
4. **반박·재반박 (옵트인, 무제한)** — "이 판단, 반박해볼까요?" 버튼으로 시작. 반박 1개 → 사용자가 **재반박** → LLM이 드러난 기준을 되비춤 → 종결 3택 **[방어했다 / 판단을 수정한다 / 보류]**. 보류는 재검토 큐로. 종결마다 "반박을 이어갈까요?"로 계속 여부는 사용자가 결정. *확정 후에도 카드 상세의 "반박 받기"로 상시 진입 가능 — 의구심은 소진되지 않는다.*
5. **Reflection** — 처음 표현 vs 지금 결론을 나란히 놓고 결론을 한 문장으로 작성 → 확정(잠금 + v1).

### 카드 상세

상황 / 현재 판단(강조) / 핵심 기준 / 선택지 비교 / 다시 볼 시점 / 판단을 바꿀 조건 / 반박과 재반박 / 판단의 변화(버전 타임라인) + [반박 받기] [다시 검토하기].

### 아카이브

시간순 단일 목록 + **검색(제목·태그 부분일치)** + 카드 뱃지(verdict, 검토 대기). 필터 칩 없음 — verdict(이력 축)와 검토 대기(주의 축)는 다른 위계라 한 줄의 배타적 필터로 섞지 않는다.

### 재검토 화면

당시의 기록(상황·결론·기준 + 접이식 선택지 비교) → 트리거 컨텍스트(조건 원문/약속) → 사건형은 [발생했다/아직이에요] → 재판단 [유지/수정/뒤집음] + 이유 → 새 버전. "아직이에요"는 큐의 다음 항목으로 이동.

### 오류 UX

LLM 쿼터·과부하(503) 시 서버가 `Retry-After`를 내려주고 클라이언트가 자동 재시도(최대 2회). 최종 실패 시 "쓰신 내용은 저장되어 있으니 같은 버튼을 다시 눌러주세요" 배너 — 대화가 서버에 저장되므로 실제로 잃는 것이 없다.

## 8. LLM 설계

### 역할 5개 (프롬프트 분리)

| 역할 | 출력 | 핵심 규칙 |
|---|---|---|
| 발견자 | 판단 후보(제목, A vs B) | 미룸·회피·습관도 판단이다 |
| 질문자 | 다음 질문 1개 + 선택지 | 선택지는 질문의 직접 답만, A vs B 재나열 금지 |
| 구조화 | 구조 JSON + 조건 분류 + 확인약속 제안 | options ≥2(구성요소 분해 금지, N개 지원), 기준은 질문형("~여부") 금지, 기존 태그 재사용 |
| 반박자 | 관점 + 반박 1개 | 표적=사용자가 사실로 여기는 믿음. 채택한 기준을 관점으로 금지(포기한 것·타 이해관계자·믿음의 오류 편에). 논점 1개·질문 1개, 제안형 금지, 논점 이동 금지 |
| 되비추기 | 재반박에서 드러난 기준 1문장 | 평가·재공격 금지 |

### 공통 가드레일

답 대필 금지 / 공감 금지 / 진단 금지 / 평가·점수화 금지 / 허용: 분석 질문과 되비추기 / JSON만 출력.

### Provider·운영

- `LlmPort` 추상화: Gemini / OpenAI / **Mock**(키 없이 전체 플로우 동작 — 심사자 실행 보장). `.env`로 전환. 현재 gpt-4o-mini 사용 중.
- 신뢰성: 5xx 1회 내부 재시도, 429는 `Retry-After` 파싱 → 클라이언트 자동 재시도.
- 비용 관측: 호출마다 `LLM_USAGE` 로그(단계·입력·출력·총 토큰). 실측: 판단 1건 ≈ 8회 호출, 입출력 ~5.2K 토큰 (thinking 포함 시 ~16K, 모델에 따라 ≈ $0.002~0.03).

## 9. 데이터 모델

```
Decision (판단) — status: DRAFT → ACTIVE (confirm 시 잠금, 단방향)
├─ title, situation, topicTag(자유), rawDiary, firstExpression
├─ criteria: string[]         ← 가치의 저울 (질문형 금지)
├─ checkInDate: date?         ← 확인 약속 — 조건과 별개, 재검토로 소진 ★
├─ DecisionOption[]           ← label + 얻는 것/포기하는 것 (전제 필드 없음 — §13)
├─ DecisionVersion[]          ← append-only, @Setter 없음 (INITIAL/MAINTAINED/REVISED/REVERSED + 이유)
├─ Condition[]                ← DATE(dueDate) | EVENT, PENDING→TRIGGERED
├─ Objection[]                ← 반박: perspective·objection·userAnswer(재반박)·reflectBack·resolution(DEFENDED/REVISED/DEFERRED), 개수 무제한
└─ FlowMessage[]              ← 기록 대화 로그 (이어서 하기·구조화·반박의 원료)
```

- DRAFT 구간은 작업대(구조 교체 허용), confirm이 커밋(잠금+v1), 이후 append-only.
- 재검토 큐 = §4의 4종을 조회 시점에 계산.

## 10. 구현 범위

### 구현 완료

- 기록 5-Step 전체 (발견·적응형 질문·구조화 승인·반박·Reflection)
- 반박·재반박: 무제한, 옵트인, 확정 후 상시 진입, 보류→큐
- 재검토 루프: 4종 트리거 + 하나씩 이어보기 + 당시 기록 컨텍스트 + append-only 버전
- 아카이브: 검색(제목·태그) + verdict/검토대기 뱃지 + 카드 상세(버전 타임라인)
- LLM 실연동(Gemini/OpenAI/Mock 전환, 재시도, 토큰 로깅) + 프롬프트 가드레일·형식 규칙
- 시드 4건(실행 즉시 재검토 큐 데모), 백엔드 테스트 12건

### 기획·설계로 대체 (README에 구분 명시)

- 판단 패턴 리포트(원시 데이터+차트 중심으로 설계 예정 — AI 요약 아님)
- 판단 트리 캔버스 시각화(Heptabase식) — 현재는 비교표가 담당
- 사건형 조건 스누즈("아직이에요 → n일간 묻지 않기") / 만료 조건 날짜 재설정
- 푸시·이메일 리마인더(모바일 웹 제약 — "열면 홈에 도착해 있는 큐"로 대체)
- 확정 판단의 제한적 수정(조건 추가 append / 서술 필드 오타 정정) — 원칙 검토됨, 미구현
- 확정 시 선택한 선택지 기록(chosenOption) → 비교표 선택 열 강조
- 계정·인증(단일 사용자), 관리자 화면(지표: LLM 실패율·판단 생성 수·재검토 전환율)

## 11. 기술 스택

| 레이어 | 선택 | 이유 |
|---|---|---|
| Backend | Spring Boot 3.5, Java 17, Gradle, Lombok, JPA, H2(file) | 가장 빠른 스택. 불변 원칙을 엔티티 설계로 강제. 외부 의존 없는 실행 |
| Frontend | Next.js(App Router), TS, Tailwind, TanStack Query | `frontend/RULES.md` 준수. 모바일 단일 컬럼 |

## 12. 심사 3관점 매핑

- **핵심 가치 플로우**: 기록→구조화→반박→카드. 실패 지점 1·2를 직접 해결하는 최소 경로.
- **운영을 성립시키는 기능**: 재검토 루프 4종 트리거 — 콘텐츠(판단 카드)가 쌓일수록 재방문 이유도 쌓인다.
- **관리·데이터 관점**: append-only로 데이터 무결성, LLM_USAGE 로그로 비용 관측, 파생 뷰 큐로 상태 동기화 버그 원천 차단.

## 13. 설계 결정의 변화 (v1 → v2, 이 문서 자체의 버전 타임라인)

이 서비스의 철학대로, 뒤집힌 설계 결정을 이유와 함께 남긴다.

| # | v1 결정 | v2 결정 | 뒤집은 이유 |
|---|---|---|---|
| 1 | 선택지마다 "핵심 전제" 행 | **전제 필드 제거** | 실데이터에서 기준과 중복 생산("~인지 여부" vs "~라고 판단함"), 이지선다에선 거울상(X vs ¬X)으로 퇴화. 검증 가능한 믿음의 역할은 '변경 조건'(반증 시나리오)이 이미 실행 가능한 형태로 수행 |
| 2 | 반박(Challenge) 최대 2개, 확정 후 2개 미만일 때만 진입 | **무제한 + 상시 진입, 이름도 Objection(반박·재반박)** | 의구심은 소진되지 않는다. 이어갈지는 매번 사용자가 결정(옵트인 유지) |
| 3 | 재검토일 제안을 DATE 조건으로 저장 | **Decision.checkInDate 분리** | 확인 약속은 판단을 바꿀 조건이 아니다(사건의 세계 vs 달력의 세계). 약속은 재검토로 소진 |
| 4 | 아카이브에 주제·상태 필터 칩 | **필터 제거, 검색으로 대체** | 태그 고정 목록은 LLM 한정의 부산물이었고, 전체/검토대기/유지/수정/뒤집음은 메타·주의·이력이라는 다른 축의 혼합이었다 |
| 5 | 홈에 최근 판단·이어서 하기 카드 | **제거 (홈 = ritual 4덩어리)** | 아카이브와 중복, 정보 과밀. 홈의 일은 재검토 큐와 기록 유도뿐 |
| 6 | topicTag 고정 5종 | **자유 태그 + 기존 태그 재사용 유도** | 분류의 한정은 근거 없음. 파편화만 프롬프트로 방지 |
| 7 | 그린 계열, 시스템 폰트 | **딥 플럼 + Noto Serif KR/Pretendard, lucide 아이콘** | Mindsera·Rosebud 레퍼런스의 "저널 무드"(세리프+딥 톤 패널). 이모지·시스템 폰트는 완성도 저해 |
| 8 | 재검토 후 무조건 홈 | **큐 이어보기** | "나머지는 이어서 보여드릴게요"라는 카피의 약속과 동작 불일치 |
